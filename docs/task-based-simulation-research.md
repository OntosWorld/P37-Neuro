# Task-based robot simulations: source assessment and engineering plan

Last reviewed: 2026-11-13. Status: **first assisted task instrument panel implemented; benchmark tasks NOT imported or qualified**.

## Product requirement

The homepage must show a robot attempting a concrete physical objective, with
a specific task, native manufacturer-derived robot geometry, real simulation
state, controls, replay provenance, an observable outcome, and negative cases.
Users should see task attempts and measurable physical interactions, rather
than disconnected joint sine waves. A contact-rich or deformable task is not
established merely because an arm or a body is moving on screen.

No claim of P37-learned execution may be made for trajectories generated by an
external scripted expert, a dataset, or direct user steering. Only the G1
experimental ONNX inference is currently attached, and it does not establish
qualified locomotion or transfer.

## Current ten embodiments: target production tasks

Tasks in the **current webpage** are small, measured, assisted-physics checkpoints.
The richer target tasks below are **integration candidates, not implemented capabilities**.

| --- | --- | --- | --- |
| Unitree G1 | Move to inspection checkpoint; base height check | Walk to a shelf, reach, recover from an obstacle | MuJoCo Playground; completed waypoint **and** upright for time window, with trained-policy provenance |
| Unitree H1 | Warehouse checkpoint | Follow a multi-turn route with recovery challenge | MuJoCo Playground / HumanoidBench; timed velocity tracking and recovery |
| Booster T1 | Short transit | Timed stand-walk-fall-recover sequence | MuJoCo Playground; fall/stand criteria from measured body and contacts |
| Unitree Go2 | Patrol checkpoint | Traverse a raised curb, turn, inspect station | ManiSkill UnitreeGo2-Reach + MuJoCo locomotion; traversed route with contact/rollover limits |
| Boston Dynamics Spot | Inspection zone | Navigate a cluttered factory aisle and return | MuJoCo Playground; route progress, collision and intervention count |
| ANYmal C | Survey checkpoint | Step across rough rocks / low obstacles to target | ManiSkill AnymalC-Reach; terrain contact, height and route checks |
| Franka Panda | Measured joint excursion | Pick and stack cubes, then try towel handling | ManiSkill/robosuite/SoftMimicGen; object grasp, lift, placement and release check |
| Universal Robots UR5e | Measured precision joint excursion | Peg insertion and bin sorting | robosuite/DexSuite; object and hole tolerance/contact check |
| Hello Robot Stretch | Delivery waypoint | Collect an item, navigate to another station, place it | Stretch MuJoCo / RoboCasa; grasp, base route, release and object terminal pose |
| Crazyflie 2 | Measured altitude change | Stabilize, fly through a gate, land | MuJoCo + tested flight controller; attitude/range/time gate predicates |

Current task panel is a **measurement harness**, not completion of the rich tasks
above. Waypoints use user-applied bounded forces to an actual floating body. Fixed
arms use recorded real joint states. Crazyflie uses its native motor model.
A measured waypoint hit is **not** learned navigation; it may happen under manual
steering. G1 policy remains experimental.

## Folding a paper / towel: special requirements

A single articulated arm waving over a flat paper-looking mesh is misleading.
Production-quality folding needs:
- independently moving/deforming sheet or cloth vertices and collision topology;
- frictional contact with fingers/end effectors, self-contact, stability and
  grounded mass properties;
- genuine bimanual grasp/regrasp for folds that require two grasp points;
- observation/action trajectories that correspond to the *same* robot asset,
  end effector, joint order, units and control rate;
- evaluated folding objective (corner alignment, crease extent, overlap,
  cloth settling), not an animation threshold.

SoftMimicGen supplies a credible research reference, but its published
towel-fold task is for YAM. To show it on P37 in a truthful manner, add
manufacturer-derived YAM or ALOHA as a supported robot **after** model/license
validation, or port/retrain an equivalent policy on a verified current
embodiment. Do not rename a YAM rollout as a Panda or G1 task.

## Architecture contract for the full task platform

1. **Task registry**: id, source revision/license, supported robot(s),
   simulator/version, scene assets and object hashes, goal, timeout, reset seed.
2. **Embodiment contract**: exact model SHA, actuator names, joint order/ranges,
   end effectors, sensors, frame conventions and controller update rate.
3. **Controller contract**: enum `human-assisted`, `scripted-expert`,
   `external-recording`, `p37-policy`; immutable model hash where applicable.
4. **Environment**: deterministic spawn positions and contacts, state capture,
   collision materials, camera and light calibration, terrain/object variations.
5. **Action execution**: bounded inputs, action normalization, explicit control
   mode and safety checks before applying controls to MuJoCo.
6. **Evaluation**: inspect actual object/robot contacts and state; task-specific
   success/failure/timeout predicates; report both successes and failures.
7. **Evidence**: record seed, task version, asset hashes, source data IDs,
   checkpoint IDs (if any), code revision, time-series observations/actions,
   result and trace replay; never manufacture success percentages.
8. **Web presentation**: task chooser -> live execution/replay -> close camera
   and physical object interaction -> results and evidence -> switch robot or task.
   No dataset download page. Navigation and controls must remain responsive.

## Phased delivery gates

**Gate A — current branch:** every one of ten models has a visible task, native
state-goal measurement and explicit qualification boundary; waypoint visualization
is added to applicable scenes. Verify browser, mobile, fixed arms, drone and
existing G1 experimental policy; the browser build must not quietly drop models.

**Gate B — source-native tasks:** port one complete Panda or UR5e pick/place
experiment, one Go2/ANYmal terrain/contact experiment, and one Stretch kitchen
delivery experiment. Each needs physical object dynamics, scripted or trained
controller, deterministic reset, measured result and video-like demo scene.

**Gate C — rich humanoid and deformable work:** qualified locomotion and
recovery, full-body manipulation where feasible, then cloth/paper folding on a
model with the required end effectors and solver. Test visual output at desktop
and mobile, with screenshots/recorded footage and negative trials.

**Gate D — cross-embodiment P37 claim:** freeze a P37 checkpoint; test the
same task on two materially different, genuinely compatible robot bodies,
including held-out evaluation. Publish the complete protocol, trials and
failed cases. External datasets or pre-trained non-P37 policies cannot prove
P37 cross-embodiment transfer.

## Immediate technical limitations

- Current web movement cycles are model-derived synthetic actuator targets;
  they were not authored from the above rich task demonstration datasets.
- Steering applies a bounded external force to a real floating base; it is not
  an actuator-level trained locomotion policy. A grounded robot may fail, fall
  or slide. Success predicates must be interpreted accordingly.
- A fixed-base arm can only satisfy the current joint-motion trial; it cannot
  pick or fold objects until an object task and controls are integrated.
- The site's target markers are non-colliding visualization props and cannot
  change the outcome. All measurements come from live native MuJoCo state.
- External datasets should be imported only after their exact license and
  robot/action schema have been checked. A demo from a different embodiment
  is not a P37 policy rollout.
